# 출퇴근 알림 여러 사용자 지원

한 서비스에서 여러 사람이 각자 계정으로 가입해, 자기 출근·퇴근 시각과 정류소·노선을 설정하고 자기 기기로만 출발 알림을 받는다. 사람마다 위젯용 JSON 주소도 따로 갖는다. 기존 [출퇴근 출발 알림 첫 버전](../commute-departure-notice/spec.md)(1인용, 공용 비밀 키)을 대체하는 확장이다.

연결된 소스:
- [PRODUCT.md](../../../PRODUCT.md) — 앱 전체 전제. 적용되는 제약은 아래 "확정된 제약"에 옮겼다. "친구에게 공유할 때 어떤 방식으로 할지"가 Unknown으로 남아 있는데, 이 스펙이 그 답이다.
- [accounts-and-access](../../decisions/accounts-and-access.md) — 로그인 방식, 가입 범위, 사용자별 접근. 이 계약을 따른다.
- [hosting-and-scheduling](../../decisions/hosting-and-scheduling.md) — 배포·저장소·매분 정시 발송. 그대로 유지한다.
- [ui-composition](../../decisions/ui-composition.md) — 로그인·가입 화면의 component·상태 표현 규칙.
- [dependency-versions](../../decisions/dependency-versions.md) — 새 의존성을 추가할 때의 버전 기준.
- [출퇴근 출발 알림 첫 버전](../commute-departure-notice/spec.md) — 알림 내용, 시각 규칙, 날씨·버스 출처는 그 스펙의 수용 기준을 그대로 따른다. 여기서는 사용자별로 달라지는 부분만 다룬다.

## 사용자에게 보이는 결과

1. 처음 방문한 사람은 로그인 화면을 본다. 초대 코드, 이메일, 비밀번호를 입력해 가입하면 바로 로그인된 상태로 설정 화면이 열린다.
2. 로그인하면 자기 출근·퇴근 설정(출발 시각, 정류소 번호, 노선 번호, 알림 시점)만 보이고 저장한다.
3. 같은 계정으로 컴퓨터와 iPhone 홈 화면 앱에 로그인하면 두 기기에서 모두 알림을 켤 수 있다. 알림은 그 사용자의 기기에만 온다.
4. 출근하는 날 각자의 출발 시각 N분 전에 각자의 설정대로 알림이 온다. 같은 시각을 설정한 사람이 여럿이어도 각자 한 번씩 받는다.
5. 설정 화면에서 자기 위젯용 JSON 주소를 확인하고, 필요하면 새로 발급받는다.

## 승인된 범위

- 이메일+비밀번호 가입·로그인·로그아웃
- 초대 코드로 가입 제한(코드는 배포 환경변수)
- 출근·퇴근 설정, 푸시 구독, 발송 기록을 사용자별로 분리
- 사용자별 정시 발송(기존 매분 깨우기 방식 유지)
- 사용자별 개인 토큰 위젯 JSON 주소와 토큰 재발급
- 기존 1인용 접근 방식(공용 `APP_SECRET`, `?key=` 주소) 중단

## 수용 기준

- AC1. 로그인하지 않고 설정 화면을 열면 설정 대신 로그인 화면이 보인다. 설정이나 다른 사람의 정보는 보이지 않는다.
- AC2. 올바른 초대 코드, 아직 가입하지 않은 이메일, 8자 이상 비밀번호로 가입하면 별도 인증 메일 없이 바로 로그인되어 설정 화면이 열린다.
- AC3. 초대 코드가 비었거나 틀리면 가입되지 않고 이유가 보인다. 이미 가입한 이메일이거나 비밀번호가 8자 미만이어도 가입되지 않고 이유가 보인다.
- AC4. 가입한 이메일과 비밀번호로 로그인되고, 틀린 비밀번호는 거절되며 이유가 보인다. 로그아웃하면 다시 로그인 화면이 보인다.
- AC5. 로그인 상태는 새로고침이나 브라우저 재시작, iPhone 홈 화면 앱 재실행 뒤에도 유지된다.
- AC6. 사용자 A가 저장한 출근·퇴근 설정은 사용자 B에게 보이지 않고, B가 저장해도 A의 설정은 바뀌지 않는다. 각 사용자는 출근·퇴근 설정을 하나씩 가진다.
- AC7. 정류소·노선 확인, 알림 시점(기본 10분), 시각 입력 규칙은 [첫 버전](../commute-departure-notice/spec.md)의 AC2–AC4와 같다.
- AC8. 알림 켜기로 만든 푸시 구독은 로그인한 사용자에게 속한다. 한 사용자가 여러 기기를 켜면 모두 받고, 테스트 알림과 정시 알림은 그 사용자의 기기에만 간다. 다른 사용자의 기기에는 가지 않는다.
- AC9. 출근일(월–금) 각 사용자의 출발 시각 N분 전 그 분 안에, 그 사용자의 구독된 모든 기기에 알림이 한 번씩 온다. 같은 날 같은 사용자의 같은 알림은 두 번 오지 않는다. 알림 문구와 날씨·버스 내용은 첫 버전의 AC9–AC11과 같다.
- AC10. 같은 분에 여러 사용자의 알림이 걸려도 각자 발송된다. 한 사용자의 발송이 실패해도 다른 사용자의 발송은 이어진다.
- AC11. 알림을 보낼 때마다 어느 사용자의 어느 쪽(출근·퇴근)인지, 예정 시각, 실제 발송 시각, 성공한 기기 수를 기록한다. 사용자는 다른 사용자의 기록을 읽을 수 없다.
- AC12. 설정 화면에 자기 위젯용 JSON 주소가 보이고, 그 주소를 열면 첫 버전의 AC12와 같은 형식으로 자기 설정 기준 정보(오전 출근, 오후 퇴근)가 나온다. 토큰이 틀리거나 없으면 내용이 나오지 않는다.
- AC13. 토큰을 다시 발급하면 이전 주소는 더 이상 열리지 않고 새 주소만 열린다.
- AC14. 어떤 화면이나 주소로도 다른 사용자의 설정·구독·발송 기록·위젯 정보를 읽거나 바꿀 수 없다. 사용자 A의 로그인 상태나 토큰으로 B의 데이터를 요청하면 거절된다.
- AC15. 옛 1인용 방식(`?key=<APP_SECRET>` 설정 화면, 공용 키 위젯 주소)은 더 이상 열리지 않는다.
- AC16. 화면 문구는 한국어이고 모든 시각은 한국 시간(Asia/Seoul) 기준이다.

## 확정된 제약과 근거

- 로그인은 Supabase Auth 이메일+비밀번호, 가입은 초대 코드, 메일 인증 없음, 위젯은 개인 토큰이다. 근거는 [accounts-and-access](../../decisions/accounts-and-access.md)에 있다. (사용자 확정: 로그인 방식, 가입 범위)
- 배포는 Vercel Hobby, 저장은 Supabase, 정시 발송은 Supabase `pg_cron`이 매분 앱을 깨우는 방식 그대로다. ([hosting-and-scheduling](../../decisions/hosting-and-scheduling.md))
- 서비스는 정보만 보여 주고 걸을지 탈지 판단하지 않는다. "버스 추천" 같은 문구를 넣지 않는다. 걷는 날을 위한 별도 기능도 두지 않는다. 서울 시내버스만 다룬다. 알림은 두 줄 안팎으로 짧게 쓴다. (PRODUCT.md)
- 알림 시각 규칙, 날씨·버스 데이터 출처, 도착 예정 시각 표시 방식은 첫 버전과 같다. 이번 변경은 "누구의 설정과 기기로"만 바꾼다.

## 가정 (바꿀 수 있음)

- 기존 1인용 데이터(설정, 푸시 구독, 발송 기록)는 이관하지 않고 전환 시 버린다. 이미 쓰던 사람(보람)이 새로 가입해 설정을 다시 입력하고 기기마다 알림을 다시 켠다. 이관이 필요하면 알려 주면 된다.
- 비밀번호 규칙은 8자 이상이다. 그 밖의 복잡도 조건은 두지 않는다.
- 위젯 토큰은 가입할 때 자동 발급되고, 설정 화면에서 보고 다시 발급한다.
- 공휴일 처리와 보안 하드닝은 이번에도 범위 밖이다(AGENTS.md 검증·리뷰 예산).
- 로그인·가입 화면은 일반적인 폼이라 별도 프로토타입 없이 [ui-composition](../../decisions/ui-composition.md)을 따라 만든다. (일상적인 화면 구성이라 에이전트가 판단)
- iPhone 홈 화면 앱의 로그인 유지(AC5)는 Supabase 세션이 앱 안의 저장소에 남는다는 전제다. 구현 때 실기기로 확인한다.

## 범위 밖과 이유

- 비밀번호 재설정, 이메일 변경, 계정 삭제 — 메일 발송이 필요하고 기본 메일 서버는 친구에게 보낼 수 없다. 아래 미뤄 둔 결정 참고.
- Google 등 소셜 로그인, 메일 링크 로그인 — [accounts-and-access](../../decisions/accounts-and-access.md)에서 기각.
- 관리자 화면, 사용자별 사용량 한도 — 가입자가 친구 몇 명 수준이라는 전제. 넘으면 계약의 재검토 조건.
- 걸었는지 버스를 탔는지 기록, 걸을지 탈지 자동 판단 — PRODUCT.md 경계와 미정.
- 발송 실패 시 재시도 — 별도 후속 과제(`docs/follow-ups/dispatch-claim-not-retried-on-failure.md`). 다만 AC10대로 한 사용자의 실패가 다른 사용자를 막아서는 안 된다.
- 공휴일 처리, 보안 하드닝 — AGENTS.md 검증·리뷰 예산.

## 미뤄 둔 결정

- 비밀번호 재설정과 계정 삭제. 그때까지의 임시 동작: 운영자가 Supabase 대시보드에서 비밀번호를 바꾸거나 계정을 지우고, 사용자는 운영자에게 요청한다. 다시 여는 계기: 외부 SMTP를 연결하기로 할 때, 또는 비밀번호를 잊은 사용자가 처음 나올 때. 추적 이슈는 아직 없다.

## 남은 위험

- 초대 코드가 퍼지면 모르는 사람이 가입한다. 가입한 사람은 위젯·알림으로 공공데이터를 호출하게 된다. 코드를 바꾸면 이후 가입은 막지만 이미 가입한 계정은 남는다.
- 공공데이터포털 일일 호출 한도는 확인하지 못했다. 사용자가 늘면 한도에 닿아 그날 알림에 날씨나 버스 정보가 빠질 수 있다(첫 버전 AC11대로 알림 자체는 간다).
- 같은 분에 걸린 사용자가 많아지면 한 번의 깨우기 호출 안에 발송이 끝나지 않을 수 있다. 가입자가 친구 몇 명 수준이라는 전제이고, 실행 시간 한도는 확인하지 못했다.
- Supabase 무료 프로젝트 일시 정지 위험은 첫 버전과 같다.
- 비밀번호를 잊으면 운영자가 직접 처리해야 한다(미뤄 둔 결정 참고).

## Setup before implementation

- Supabase 대시보드 Authentication에서 Email 로그인을 켜고 "Confirm email"을 끈다 — 인증 메일 없이 가입하기 위해(AC2). 완료 조건: Authentication > Sign In / Providers에서 Email이 켜져 있고 Confirm email이 꺼져 있다.
- Supabase 대시보드 Authentication에서 "Allow new users to sign up"을 끈다 — 공개 키로 가입 API를 직접 불러 초대 코드를 건너뛰지 못하게 하기 위해(AC3). 계정은 서버가 관리자 권한으로 만든다. 완료 조건: 그 토글이 꺼져 있고, 공개 키로 가입 API를 직접 호출하면 가입이 거절된다.
- 초대 코드를 정해 Vercel 환경변수(예: `SIGNUP_INVITE_CODE`)에 넣는다 — 가입 제한(AC3). 완료 조건: Vercel 프로젝트 Environment Variables 목록에 해당 변수가 Production과 Preview에 있다. (값은 대화나 문서에 적지 않는다.)
- 브라우저에서 쓸 Supabase 공개용 키(`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`)가 Vercel 환경변수에 있다 — 브라우저 로그인 세션(AC4, AC5). 완료 조건: Vercel 환경변수 목록에 있고, Supabase 대시보드의 API Keys 공개용 키와 같은 값이다.
