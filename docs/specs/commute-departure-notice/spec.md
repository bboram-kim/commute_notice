# 출퇴근 출발 알림 첫 버전

출근·퇴근 출발 시각과 서울 버스 정류장·노선을 한 번 설정해 두면, 출근하는 날마다 출발 10분 전에 그날 비·눈 여부와 기온, 버스 도착 예정 시각을 컴퓨터와 iPhone에 웹 푸시로 알린다. iPhone 위젯(Scriptable)이 읽을 JSON 주소도 함께 연다.

연결된 소스:
- [PRODUCT.md](../../../PRODUCT.md) — 앱 전체 전제. 이번 작업에 적용되는 제품 제약은 아래 "확정된 제약"에 옮겨 두었다.
- [hosting-and-scheduling](../../decisions/hosting-and-scheduling.md) — 배포 위치, 저장소, 정시 발송을 무엇이 깨우는지. 이 계약을 따른다.
- [ui-composition](../../decisions/ui-composition.md) — 설정 화면의 component·token·상태 표현 규칙.
- [dependency-versions](../../decisions/dependency-versions.md) — 웹 푸시 등 새 의존성을 추가할 때의 버전 기준.

## 사용자에게 보이는 결과

1. 설정 화면에서 출근·퇴근 각각의 출발 시각, 정류소 번호, 노선 번호를 저장한다. 저장하면 정류소 이름과 노선이 맞게 찾아졌는지 보인다.
2. 컴퓨터 브라우저와 iPhone(홈 화면에 추가한 앱)에서 각각 알림을 켤 수 있다.
3. 출근하는 날 출발 10분 전에 알림이 온다. 예:
   ```text
   08:00 출발 · 비 2mm · 3°C
   146번 08:04 도착 (출발 4분 뒤) · 다음 08:19
   ```
4. 퇴근 출발 시각 10분 전에도 같은 모양의 알림이 온다.
5. 비밀 키가 붙은 JSON 주소를 열면 지금 시각에 가까운 쪽(출근 또는 퇴근)의 날씨와 버스 도착 예정 정보가 나온다.

## 승인된 범위

- 출근·퇴근 두 벌의 설정(출발 시각, 정류소 번호, 노선 번호, 알림 시점)
- 컴퓨터(Chrome·Edge)와 iPhone(iOS 16.4 이상, 홈 화면 설치) 웹 푸시 구독
- 출근일 출발 N분 전(기본 10분) 알림 1회씩
- 위젯용 JSON 주소
- 로그인 없는 1인용, 비밀 키로 보호되는 설정 화면과 JSON 주소
- 발송 기록(발송 후 점검에 사용)

## 수용 기준

- AC1. 비밀 키 없이 설정 화면이나 JSON 주소를 열면 내용이 보이지 않고, 올바른 키가 붙은 주소로만 열린다.
- AC2. 설정 화면에서 출근·퇴근 각각의 출발 시각(시:분), 서울 버스 정류소 번호(5자리 `arsId`), 노선 번호를 저장할 수 있다. 저장 후 다시 열면 그대로 보인다.
- AC3. 정류소 번호와 노선 번호를 저장하면 해당 정류소 이름이 표시된다. 그 정류소에 없는 노선이거나 없는 정류소 번호면 저장하지 않고 이유를 보여 준다.
- AC4. 알림 시점(출발 몇 분 전)을 바꿀 수 있고 기본값은 10분이다.
- AC5. 컴퓨터 브라우저에서 알림 켜기를 하면 구독이 저장되고, 테스트 알림을 눌렀을 때 OS 알림이 뜬다.
- AC6. iPhone에서 홈 화면에 추가하지 않고 열면 홈 화면 추가 방법을 안내하고, 추가한 앱에서 알림 켜기를 하면 테스트 알림이 iPhone에 뜬다.
- AC7. 출근일(월–금) 출근 출발 시각의 N분 전 그 분 안에, 구독된 모든 기기에 알림이 한 번씩 온다. 같은 날 같은 알림이 두 번 오지 않는다.
- AC8. 퇴근에도 AC7이 같은 방식으로 적용된다.
- AC9. 알림에는 출발 시각, 출발 시각이 속한 시간대의 강수 형태(없음·비·비/눈·눈·소나기)와 강수량 또는 적설량, 기온이 들어간다. 날씨는 설정한 정류소 위치 기준이다.
- AC10. 알림에는 설정한 노선의 다음 두 대의 도착 예정 시각과, 첫 번째 버스가 출발 시각보다 몇 분 앞서거나 뒤에 오는지가 들어간다.
- AC11. 운행 전·운행 종료 등으로 도착 예정 버스가 없으면 알림에 "도착 예정 버스 없음"이 들어간다. 날씨나 버스 조회가 실패하면 실패한 쪽만 "정보를 가져오지 못했습니다"로 표시하고, 알림 자체는 보낸다.
- AC12. JSON 주소는 오전(12시 전)에는 출근, 오후에는 퇴근 설정 기준으로 출발 시각, 날씨(강수 형태·강수량 또는 적설량·기온), 다음 두 대의 도착 예정 시각(ISO 8601, 한국 시간), 조회 시각을 돌려준다.
- AC13. 알림을 보낼 때마다 어느 쪽(출근·퇴근), 예정 시각, 실제 발송 시각, 성공한 기기 수를 기록한다.
- AC14. 모든 시각은 한국 시간(Asia/Seoul) 기준이다.

## 확정된 제약과 근거

- 배포는 Vercel Hobby, 저장은 Supabase, 정시 발송은 Supabase `pg_cron`이 매분 앱을 깨우는 방식이다. Vercel Hobby의 예약 실행은 15–59분 오차가 있어 출발 알림에 쓸 수 없다. (사용자 확정, [hosting-and-scheduling](../../decisions/hosting-and-scheduling.md))
- 로그인 없는 1인용이다. 로그인을 넣으면 첫 버전이 크게 늘고, Scriptable 위젯은 로그인 세션을 들고 다니기 어려워 어차피 키가 필요하다. 설정 화면과 JSON 주소는 배포 환경변수에 둔 비밀 키가 주소에 있어야 열린다. (사용자 확정)
- 알림은 출발 N분 전 1회, 기본 10분. 버스는 "몇 분 남음"이 아니라 도착 예정 시각과 출발 시각 기준 차이로 보여 준다. 알림을 늦게 열어도 숫자가 틀어지지 않는다. 출발 직전의 최신 값은 위젯이 맡는다. (사용자 확정)
- 출근과 퇴근을 모두 넣는다. 같은 방식이라 추가 비용이 작고, 퇴근 시간을 버스에 맞추는 가치를 첫 버전에서 확인한다. (사용자 확정)
- 서비스는 정보만 보여 주고 걸을지 탈지 판단하지 않는다. "버스 추천" 같은 문구를 넣지 않는다. (PRODUCT.md)
- 걷는 날을 위한 별도 기능을 두지 않는다. 비·눈이 없는 날에도 알림은 출근일마다 온다. (PRODUCT.md, 사용자 확정)
- 서울 시내버스만 다룬다. (PRODUCT.md)
- 알림은 한눈에 읽을 수 있게 두 줄 안팎으로 짧게 쓴다. (PRODUCT.md 경험 원칙)
- 데이터 출처: 버스는 서울특별시 정류소정보조회 서비스의 `getStationByUid`(`arsId` 기준, 노선명 `rtNm`, 정류소명 `stNm`, 좌표 `gpsX`·`gpsY`, 도착 정보 `traTime1`·`traTime2`·`arrmsg1`·`arrmsg2`). 날씨는 기상청 단기예보 조회서비스(강수 형태 `PTY`, 강수량 `PCP`·`RN1`, 적설 `SNO`, 기온 `TMP`·`T1H`). 정류소 좌표를 기상청 격자로 바꿔 날씨를 조회한다.

## 가정 (바꿀 수 있음)

- 출근일은 월–금이고 공휴일은 구분하지 않는다. 공휴일에도 알림이 온다.
- 출발 시각이 속한 시간대의 날씨는 발송 시점에 가장 가까운 예보(초단기예보)를 쓴다.
- Scriptable 위젯 스크립트 자체는 이번 범위가 아니다. JSON 주소만 연다.
- 비밀 키를 잃거나 바꾸려면 배포 환경변수를 바꾼다. 앱 안에 키 변경 기능은 없다.
- 설정 화면은 일반적인 폼이라 별도 프로토타입 검토 없이 [ui-composition](../../decisions/ui-composition.md)을 따라 만든다. (일상적인 화면 구성이라 에이전트가 판단)
- 화면 문구는 한국어다.
- `traTime1`의 단위(초 또는 분)는 레퍼런스마다 다르게 적혀 있다. 구현 때 실제 응답의 `arrmsg1`과 비교해 확정한다.

## 범위 밖과 이유

- 로그인, 여러 사용자, 친구 공유 — 1인용으로 확정. 아래 미뤄 둔 결정 참고.
- 걸었는지 버스를 탔는지 기록 — PRODUCT.md에서 미정.
- 배차 실측 기록, 혼잡도, 기상특보 전날 알림 — 이번 요청에 없음.
- 걸을지 탈지 자동 판단 — PRODUCT.md 경계.
- 공휴일 처리, 보안 하드닝 — AGENTS.md 검증·리뷰 예산.

## 미뤄 둔 결정

- 친구 공유 방식(로그인을 붙일지, 친구가 각자 배포할지). 그때까지는 1인용이다. 다시 여는 계기: 사용자가 친구에게 공유하겠다고 할 때. 추적 이슈는 아직 없다.

## 남은 위험

- Supabase 무료 프로젝트는 7일간 활동이 없으면 일시 정지된다. 매분 예약 실행이 활동으로 인정되는지 공식 문서에서 확인하지 못했다. 정지되면 알림이 오지 않는다. 아래 발송 후 점검으로 확인한다.
- iPhone 웹 푸시는 홈 화면에 설치한 앱에서만 오고, iOS가 알림 전달을 늦추거나 묶을 수 있다.
- 버스 도착 예정 시각은 알림 발송 시점 값이라, 출발까지 10분 사이에 버스가 늦어지거나 빨라질 수 있다.
- 공공데이터포털 API가 응답하지 않으면 그날 알림에 날씨나 버스 정보가 빠진다(AC11).

## Setup before implementation

- 공공데이터포털(data.go.kr) 계정과 "서울특별시_정류소정보조회 서비스" 활용 신청 — 버스 도착·정류소 정보(AC3, AC10). 완료 조건: 발급 키로 `getStationByUid`를 브라우저나 curl로 직접 호출해 정상 응답(정류소명 포함)을 받는다.
- 같은 계정으로 "기상청_단기예보 ((구)_동네예보) 조회서비스" 활용 신청 — 날씨(AC9). 완료 조건: 발급 키로 초단기예보를 직접 호출해 정상 응답을 받는다.
- Supabase 프로젝트(무료) 생성 — 설정·구독·발송 기록 저장과 `pg_cron` 실행. 완료 조건: 대시보드에서 프로젝트가 활성 상태이고 Extensions에서 `pg_cron`, `pg_net`을 켤 수 있다.
- Vercel 계정(Hobby)과 이 저장소를 배포할 프로젝트 — iPhone 구독에 필요한 공개 HTTPS 주소. 완료 조건: Vercel 대시보드에 프로젝트가 있고 배포 주소가 HTTPS로 열린다.
- iPhone의 iOS 버전 16.4 이상 — iPhone 웹 푸시(AC6). 완료 조건: 설정 > 일반 > 정보에서 버전을 확인한다.

## Post-release check

- 지표: 출시 후 출근일의 출근·퇴근 알림 중 예정 시각 1분 안에 발송 기록이 있는 비율
- 통과 기준: 100% (빠진 날이나 1분 넘게 늦은 발송이 없음)
- 기간: 출시 후 14일
- 측정: `docs/specs/commute-departure-notice/check-send-timeliness.ts` — Supabase의 발송 기록(AC13)과 저장된 출퇴근 설정을 읽어, 기간 안의 월–금마다 출근·퇴근 예정 발송이 1분 안에 있었는지 세고, 빠지거나 늦은 날짜 목록과 함께 PASS 또는 FAIL을 출력한다.
- 기준 미달 시: 빠진 날이 Supabase 일시 정지 때문인지 확인하고, 그렇다면 [hosting-and-scheduling](../../decisions/hosting-and-scheduling.md)의 "Reconsider when"에 따라 실행 환경 결정을 다시 연다.
